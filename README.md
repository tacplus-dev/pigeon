# pigeonhost

The generic pigeon host, a tacplus platform service (registry `pigeonhost`, id 107; the
protocol it speaks is package `pigeon`, in the coop's `shared/pigeon.proto`). It never runs as a
Deployment: the coop (github.com/tacplus-dev/coop) creates one Kubernetes Job per pigeon with
this image, an identity kernel minted for the run (`<service>/workloads/pigeon-<run_id>`, a
bootstrap token in the Job's Secret, `KERNEL_BOOTSTRAP_TOKEN_FILE`), and the run in its
environment (`PIGEON_RUN_ID`, `PIGEON_THREAD_ID`, `PIGEON_TENANT`, `PIGEON_KIND`, `PIGEON_CALLER`).

It serves no RPC. It lives on its run's thread of `coop.PigeonMessageBus.stream`: it says
`Ready`, does each `PigeonTask` its dog (the caller) puts there with the kind it was started as,
answers with a `PigeonResult`, and exits when the coop says the run has ended. Tasks from any
other sender are dropped; a task naming another kind fails `INVALID_TASK`.

Built-in kinds are the platform's: `echo.ping` (the result is the request) proves the round
trip. A product's kind, such as SeaBeam's Texas 811 filing, is that product's own host built on the
same protocol (`coop/proto/shared/pigeon.proto`).

`tacplus/` is generated by `tacplus build` and not committed.

## Releases

pigeon is released by version, and fleets pin a release line, `MAJOR.MINOR`, which is always that line's
highest patch ([tacplus#180](https://github.com/tacplus-dev/tacplus/issues/180)). Versions are `0.x` until
SeaBeam's launch (2026-12-01), when `1.0.0` is cut; on `0.x` a minor may break, a patch never does.

A change merged to main is released by the same run that merged it: a fix as the next patch, a feature as the
next minor. To cut one, from the commit to release (a green commit of main):

```sh
git tag -a v0.1.4 -m v0.1.4   # vMAJOR.MINOR.PATCH; a patch to an older line is tagged on release/MAJOR.MINOR
git push origin v0.1.4
```

The tag runs [release.yml](.github/workflows/release.yml): the gates on the tag, in the build image its
`tacplus.lock` pins ([ci/release-build.sh](ci/release-build.sh)), then `ghcr.io/tacplus-dev/pigeon:<version>`
for linux/arm64 ([ci/release-image.sh](ci/release-image.sh); amd64 is off, as in the fleets: `PLATFORMS` in
release.yml turns it on), labelled with the version and commit (`org.opencontainers.image.version`,
`.revision`), and `:<MAJOR.MINOR>` moved to it only when it is the line's highest patch, so the line tag never
goes backwards and no other line moves ([ci/release-tags.sh](ci/release-tags.sh)). The GitHub release carries
the static binaries and the commits since the previous release ([ci/release-notes.sh](ci/release-notes.sh)),
and is marked Latest only when it is the highest release of all ([ci/release-latest.sh](ci/release-latest.sh)).
A pre-release (`v0.2.0-rc.1`) publishes only its own tag. The package is public: pulls need no credential.

Running the workflow by hand publishes a tag that already exists, as its push would have
(`gh workflow run release.yml -f tag=v0.1.0 -f publish=true`; the releases tagged before the workflow existed
are published this way). Without `publish` it is a dry run (`gh workflow run release.yml -f tag=v0.1.4`):
it builds the tag, or this commit tagged locally as a version not tagged yet, prints the tags and notes that
release would get, and publishes nothing. A looper's token cannot dispatch a workflow (no `actions: write`),
so it sends the same as the `repository_dispatch` event `release`:

```sh
gh api repos/tacplus-dev/pigeon/dispatches --input - <<'EOF'
{"event_type": "release", "client_payload": {"tag": "v0.1.0", "publish": "true"}}
EOF
```

The scripts are tested by `go test ./ci/`.

The image runs under the [launcher](https://github.com/tacplus-dev/launcher), built from source at the commit
`LAUNCHER_COMMIT` in release.yml names.
